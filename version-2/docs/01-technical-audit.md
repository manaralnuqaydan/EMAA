## 4. Camera privacy (verified from code)

- Frames are processed **in the browser** by MediaPipe Hands to find the hand.
- For Arabic mode a cropped hand image (JPEG) is sent to the **local** API on `localhost:8000` on every prediction; for ASL mode only 21 landmark coordinates are sent.
- The API does **not** write images to disk and does not log request bodies (`model/api.py` has no `imwrite`, `print` or logging of inputs).
- No camera data goes to an external API. The chatbot receives **text only**.
- MediaPipe's JavaScript is downloaded from cdn.jsdelivr.net (code only; frames are not uploaded).
- If the API were deployed to a remote server, hand crops would leave the device; this needs a consent notice before any hosting.

## 6. Risks

1. **Scope vs. data.** Word-level Saudi Sign Language needs a labelled video dataset (e.g. KArSL). None is in the project; licence must be checked.
2. **ASL datasets are video, non-commercial, and large.** Training a temporal model on CPU only (this environment has no GPU) limits vocabulary size; a landmark-based model on a subset (≈100 signs) is realistic, 2,000 signs is not.
3. **Exhibition = public demonstration.** All four ASL datasets are research/non-commercial licences; showing a model at an exhibition needs to be checked against each licence (Phase 2).
4. **Avatar word signs.** There is no animation library. Word signs would have to be built from motion data (landmarks from dataset videos) or hand-authored; each must be labelled honestly as such.
5. **Chatbot depends on an API key** and internet access at the venue.
6. **Hard-coded `localhost` API URL** prevents any hosted demo.
